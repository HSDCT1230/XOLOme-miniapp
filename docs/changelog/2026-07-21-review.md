## 审查发现（代码 vs README 状态机不一致）
1. 【严重】LOCKED 状态从未被任何代码设置，但 payment 的 FINAL 预支付要求 status==='LOCKED' → 尾款支付链路不可达，用户付完意向金+补足金后无法付尾款。需补一条 DEPOSIT_CONFIRMED→LOCKED 的流转（建议补足金成功后或尾款预支付校验时触发）。
2. 【严重】SHIPPED 状态从未被写入（shippedAt 字段亦无人更新），README 中的 LOCKED→FINAL_PAID→SHIPPED 链路断裂。
3. EXPIRED 被列为终态但无任何代码设置（仅 order.create 的 nin 校验引用），是幽灵状态。
4. VOUCHER_USED 逻辑存疑：voucher.use 把目标新订单直接置为 VOUCHER_USED，使其永远无法再走 PENDING_DEPOSIT→DEPOSIT_PAID；且未做任何金额抵扣，代金券实际未生效。
5. refund.js 把 DEPOSIT_VOUCHER / CONFIRMED_VOUCHER 列入可退款名单，但与"宽限期过→转代金券(放弃退款)"的产品规则矛盾。
6. notification 的订阅消息 data 写死 thing1/time2 且 templateId 为占位符（tmpl_xxx），上线前需替换为真实模板ID且字段需逐模板匹配；time2 用 toLocaleString('zh-CN') 易超 20 字符被拒。
7. notification 深链 page 写的是 'pages/order/detail'，但 app.json 中页面路径是 'pages/order-detail/order-detail'，点通知进错页。
8. refund 调用 cloud.cloudPay.refund 传的是 lastPayment.transactionId 作为 outTradeNo；云支付退款接口需原始 outTradeNo，当前未存储，建议下单时把 outTradeNo 存进 payments 再回传。
9. 支付成功逻辑在 payment.handlePaymentSuccess 与 mockPayment 中重复实现，存在漂移风险，建议抽公共模块。
10. order.create 库存校验 count→add 非原子，并发可能超卖（3000限量）。
